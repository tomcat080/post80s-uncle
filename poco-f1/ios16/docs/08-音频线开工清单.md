# 08 - 音频线开工清单（P0 盘点）

状态：只读盘点完成，未改内核、未刷机。以下每条都在真机/本机构建产物上核过。

## 1. 系统侧现状（iOS 16.7.16 image）

| 事实 | 证据 | 含义 |
|---|---|---|
| 音频 HAL 插件被禁用 | `/Library/Audio/Plug-Ins/HAL/` 为空；`VirtualAudio.plugin` 在 `HAL.disabled/` | v12 起为了不让 `mediaserverd` 反复 SIGSEGV 手动挪走的 |
| 没有虚拟音频设备 | `sweetps` 里没有 media/audio 常驻；`/dev` 无 audio/pcm 节点 | 插件找不到可用的 VAD，`vdef` 不存在 → HAL 里拿不到默认设备 |
| 没有 `/product/audio` 设备树节点 | `beryllium-16.adt` 里 `\0audio\0` 计数为 0；插件里写死 `IODeviceTree:/product/audio` | 插件启动时连"有哪些端口"都读不到 |
| 内核里没有音频类 | `kernel.development.sweet` 里 `IOAudio*` 命中 0，只有 `COREAUDIO` 字样 | 既没有 `IOAudioFamily`，也没有 `AppleEmbeddedAudio` 这类内置驱动 |
| 内核有 DriverKit 基础设施 | kernel 里有 `dext` 启动/rematch/UniqueID 整套字符串，`IOUserServer` 相关 29 处 | dext 机制在，缺的是音频 dext 本身 |
| 设备上没有音频 dext | `/System/Library/DriverExtensions` 只有 HID×2、BCMWLAN、E1000/IXGBE/IXL、ECM | 没法"直接加载 Apple 的音频驱动" |

`VirtualAudio.plugin`（6,657,136 B，已取回本机 `/tmp/VirtualAudio.bin`）的关键 strings：

```
IODeviceTree:/product/audio
VirtualAudioDevice_Default / _Music / _LowLatency / _CallContinuity / _SiriOutput ...
Created DriverKit device
kAppleEmbeddedAudio_DevicePropertyInputEnableDevice
com.apple.audio.virtualaudio
```

结论：iOS 16 的音频是 **HAL 插件（用户态）+ 内核/dext 驱动**两层。插件负责路由与端口策略，
真正的流由驱动侧（DriverKit AudioDriverKit，或内置 `AppleEmbeddedAudio`）提供。
两者在这台机器上都缺。

## 2. 硬件侧事实（beryllium / SDM845）

Linux 主线 DTS（`sdm845-xiaomi-beryllium-common.dtsi` + `sdm845-wcd9340.dtsi`）给出的链路：

```
Q6ADSP 固件（q6afe / q6asm） --> SLIMBUS_0_RX --> WCD9340 codec
                                                   ├─ codec@1,0 (slim217,250), ifd@0,0 同总线
                                                   ├─ SoundWire master swm@c85 (v1.3.0, 6 dout / 2 din)
                                                   ├─ MCLK = RPMH_LN_BB_CLK2, 9.6 MHz
                                                   └─ IRQ = TLMM gpio 54
```

要点：
- **codec 只在 SLIMbus 上**，SLIMbus 主控在 SDM845 上是 LPASS 里的 NGD，**由 ADSP 固件驱动**
  （Linux 侧是 `qcom,slim-ngd`，走 GLINK/QMI 到 ADSP，不是 HLOS 直接寄存器操作）。
- 扬声器功放挂在 codec 内部的 SoundWire（`swm`），同样要 codec 先活。
- 因此"真出声"的必要条件 = **ADSP 起来**（PIL 加载 `adsp` 分区固件）+ Q6AFE 路由 + codec 初始化。
  这比 MSS/MBA 那套只多不少：ADSP 是完整 DSP 固件（几十 MB 级），还带 GLINK/QRTR/QMI 三件套。

## 3. 两条可选路线（成本差一个数量级）

### 路线 A：先让音频栈"活着"（不发声，纯软件）
- 目标：CoreAudio/HAL 里出现一个可用设备，`mediaserverd` 不再崩，音量键/系统提示音的
  路由逻辑能跑；后续换真驱动时上层不用重做。
- 做法：内核侧提供最小播放设备（`IOAudioFamily` 已在 Apple 开源仓库
  `apple-oss-distributions/IOAudioFamily`，可作为源码引入），ADT 里补 `/product/audio` 节点，
  再把 `VirtualAudio.plugin` 从 `HAL.disabled` 放回。
- 风险：低。不碰 EL3、不碰 ADSP；最差情况是设备起不来音频设备，系统照常。
- 代价：要给内核构建引入一个 kext 工程（`IOAudioFamily` 不是 xnu 自带）。

### 路线 B：真出声（ADSP + codec）
- 前置：ADSP PIL（`adsp` 分区固件加载/校验/启动）→ GLINK/QRTR → Q6AFE 配置 SLIMbus →
  WCD9340 上电/时钟/MCLK → SoundWire 枚举功放 → 才算"有声音"。
- 风险：高。和 MSS 那次同级别甚至更高（DSP 固件 + 多套 IPC），一旦 EL3/DSP 侧卡住，
  现场只能物理断电。
- 代价：至少 5-8 个真机闸门，且每个闸门都要断电重启。

## 4. 建议的第一闸门（A0.5，仍然只读）

1. 读 `adsp` 分区是否存在、`image/adsp.mbn`（或 `adsp.mdt` + 分段）大小；
2. 读 ADSP 相关时钟/复位状态（gcc adsp CBCR、QDSP6 ADSP halt 寄存器）；
3. 确认 ADSP 是否已被 ABL 拉起（若是，路线 B 少一大截；若在复位，就得先做 PIL）。

这三项都是只读 MMIO/分区读，可以并到一次 `sweetaudio=1` 的预检里，不改任何状态。

## 5. 结论

- 现在没有任何"半成品"可以复用：既没有音频 kext/dext，也没有 `/product/audio`。
- 路线 A 能在低风险下把 iOS 音频栈恢复到"有设备、不崩"，但不会有声音；
  路线 B 才能出声，代价等同再做一个 P3。
- 用户已选路线 B。

## 6. B0 只读预检实测（stage7 / `shim-boot-aud0.img`，已完成）

镜像：`shim-boot-aud0.img` 17,330,176 B，sha256 `76f5f76e13ed6e84…f420450`，
cmdline `sweetwlan=7 sweetwlandelay=30`。补丁 `0146-beryllium-audio-adsp-preflight.patch`
（CI run `45128843473` success）。实现：`bsd/dev/beryllium_wlan.c` 新增 `wl_audio_preflight()`，
挂在 `wl.stage==7`，全部只读——不调 PAS、不释放复位、不写任何寄存器。

真机 console 六行（两次上电复现一致）：

```
SWEET AUDIO: preflight start (read-only): no PAS call, no reset, no write
SWEET AUDIO: PAS PAS_INIT_IMAGE (svc 0x02 cmd 0x1): status=0 result=1
SWEET AUDIO: PAS PAS_MEM_SETUP (svc 0x02 cmd 0x2): status=0 result=1
SWEET AUDIO: PAS PAS_AUTH_AND_RESET (svc 0x02 cmd 0x5): status=0 result=1
SWEET AUDIO: GCC lpass q6_axi CBCR 0x47000 = 0x80000000, sway CBCR 0x47008 = 0x80000000
SWEET AUDIO: ADSP 0x8c500000 +0: 00000000 00000000 00000000 00000000 (zero (firmware not loaded))
SWEET AUDIO: preflight done
```

判读：

| 项 | 结果 | 含义 |
|---|---|---|
| PAS `svc 0x02 cmd 0x1/0x2/0x5` | 全部 `status=0 result=1` | TZ 里 PIL handler 在，三条调用**可用**（`result=1` 即 IS_SUPPORTED 的 true） |
| GCC `0x47000` / `0x47008` CBCR | 都 `0x80000000` | bit31=CLK_OFF(1)，bit0=ON(0) → LPASS `q6_axi` 与 `sway` **两支时钟都是关的** |
| ADSP carve-out `0x8c500000` 首 4 word | 全 0 | ADSP 处于复位/未加载状态，**不是 ABL 已拉起**（i.e. 路线 B 省不掉 PIL） |
| 分区名 | `adsp` / `adsp_a` / `adsp_b` 均 `not found (2)` = ENOENT | GPT 里没有这些名字 |

分区真名：用 `fastboot getvar partition-size:<name>` 逐个试，直接问 bootloader（不重启内核）：

```
dsp    => 0x1FFC000      ← 命中，ADSP 固件就在这个分区（33.5 MB）
modem  => 0xBFFC000
msadp  => 0x3C000
adsp / adsp_a / adsp_b / dsp_a / dsp_b / adsps / adsps_a / adspso => GetVar Variable Not found
```

即：Xiaomi 这颗机器把 ADSP 固件放在 **`dsp`** 分区（单分区、无 A/B），
所以先前在 `wl_part_info()` 里查 `adsp*` 必然 ENOENT；`dsp` 的 size 与 `boot` 恰好都是
`0x1FFC000`，纯巧合，别混。

结论：路线 B 的两个未知量已消掉一个——**固件在 `dsp`，33.5 MB**；另一个是
**PAS 可用但从未真调**（B0 只查"可用"）。

## 7. 下一闸门 B1：先补前置，再动 PAS

Linux `qcom_q6v5_pas`（`adsp-pas`）的加载顺序是：

```
q6v5_pds_enable        → 开 rpmhpd 电源域（lpass/adsp 域）
q6v5_clk_enable        → 开 gcc lpass q6_axi / sway clamp 时钟
qcom_scm_pas_init_image → 上传元数据（segments）
qcom_scm_pas_mem_setup  → 把固件段搬到 carve-out（TZ 内部做 assign）
qcom_scm_pas_auth_and_reset → 校验 + 复位释放
q6v5_rmb_mba_wait / firmware_ready 等待
```

现在 CBCR 两支时钟都还是 CLK_OFF，若跳过 PD/时钟直接发 `PAS_AUTH_AND_RESET`，
大概率重演 P3 1a 的形态（`MEM_SETUP` 与 `ASSIGN_MEM` 同属 TZ 内存授权路径，域关着时悬挂在 EL3）。

所以 B1 的第一件事**不是**调 PAS，而是先把两线共用的 provider 做出来：

1. `sweet_pd`：RPMh 电源域（LPASS / ADSP CX+MX），`ARC_CLK` 命令走 RPMh cmd-db（SMEM `0x86000000+0x200000` 已在档）；
2. `sweet_clk`：GCC CBCR 通用 read/modify/write（`0x47000`、`0x47008` 先落地，其余按需扩）。

这两个 provider 是 **Wi-Fi P3 与音频 B 的同一条前置**：做完 MSS 与 LPASS 都能开域开时钟，
一次投入两线通。这也是把 P3 那笔欠账补上的最短路径。

B1 通过判据（只读即可判）：

- 写完 `0x47000/0x47008` bit0=1 后，回读 bit31(CLK_OFF)=0；
- 期间 console 不冻结、EL3 不悬挂（`ping` 与 SSH 都在）；
- QDSP6 ADSP 侧 halt 寄存器（`0x1f6_3000` 一族）状态随时钟打开而变化。

之后才是 B1.1：读 `dsp` 分区头（`+0` 是否为 ELF magic `0x7f454c46`，`image/adsp.mbn` 还是
`adsp.mbn` 直放），决定 `PAS_INIT_IMAGE` 的 metadata 来源。

镜像：17,330,176 B，sha256 `8e29686a41d9e871…0f221693`，cmdline = 完整基础串 + `sweetwlan=8 sweetwlandelay=30`。
补丁 `0147-beryllium-audio-dsp-scan-clken.patch`（CI run `45171710966` success），实现为
`wl_audio_stage8()`：只读 `dsp` 分区头 + 读两支 CBCR + 读 carve-out 首 word，**不写任何寄存器**。

真机 console：

```
SWEET AUDIO: stage 8 start: dsp partition scan + LPASS state read (read-only, no write)
SWEET AUDIO: dsp partition: LUN 4, 32768 KiB (0x2000000 bytes)
SWEET AUDIO: dsp +0: 00 00 ... （32 字节全 0）(not an ELF at +0 (check FAT below))
SWEET AUDIO: dsp FAT16 mount: 6 (not a FAT16 volume)
SWEET AUDIO: q6_axi 0x80000000 (CLK_OFF 1, ON 0), sway 0x80000000 (CLK_OFF 1, ON 0)
SWEET AUDIO: ADSP 0x8c500000 +0 0
SWEET AUDIO: stage 8 done
```

判读：

| 项 | 结果 | 含义 |
|---|---|---|
| `dsp` 分区 | LUN 4, 32 MiB（`0x2000000`） | 分区确实在（fastboot 报 `0x1FFC000` 是去掉 GPT 头尾后的可用长度） |
| `+0` 32 B | 全 0 | 首扇区没有 ELF / 没有卷头；可能是空分区，也可能是稀疏镜像/ext4（ext4 的 magic 在 1 KiB 偏移处） |
| FAT16 挂载 | err 6 | 不是 FAT；不能照 `modem` 那条 FAT 路径读 `image/adsp.mbn` |
| CBCR | 仍 `0x80000000` | LPASS 两支时钟在 boot 后仍是关的（没有被 ABL 打开） |
| carve-out | 仍 0 | ADSP 固件未加载 |

结论：ADSP 固件"位置"已知（`dsp` 分区），但**容器格式未知**；下一步要按偏移扫（0x400/0x1000/0x800 找 ext4 `0x53EF`、找 sparse `0x3AFF26ED`、找 `ANDROID!`、找 ELF 的 `7F 45 4C 46`），确认是"空分区"还是"带偏移的镜像"。

### 踩坑记录（重要，别再复现）

`tools/mkpayload.py --cmdline` 是**整串替换**，不是追加。只传 `"sweetwlan=8 sweetwlandelay=30"`
会把默认的 `debug/serial/rd=ufsroot0/...` 全部丢掉，症状是：

- 屏幕停在 `SWEET EARLY 20: kprintf startup complete` + 进度条不动；
- UDP console **一行都没有**（8021 端口收不到任何东西）；
- USB/ECM 完全不出现，`system_profiler` 里查不到设备，`ping 192.168.7.2` 全丢。

极易误判成"新内核起不来"。正确做法：**完整串**照抄，只改 `sweetwlan=N`：

```
debug=0xc serial=3 cpus=8 keepsyms=1 -noprogress rd=ufsroot0 unentitled_ios_sim_launch=1
ignition_level=1 wdt_test=no_user_checkin ufsrw=1 rootrw=1 launchd_unsecure_cache=1 wdt=-1
sweetfb_noconsole=1 sweetfb_hz=30 sweetfb_vsync=1 sweetfb_scale=1 sweetfb_flip=1 sweetusb=2
sweetbattery=1 sweetsample=- sweetwlan=N sweetwlandelay=30
```

打包后必须回读校验：`payload.bin` 的 `0x48..0x48+608` 就是 cmdline 区，`split(b'\0')[0]` 应能看到
`rd=ufsroot0` 与 `sweetwlan=N` 同时存在，再拿去 mkbootimg。
