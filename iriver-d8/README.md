# iRiver D8 固件恢复

> 一台老 iRiver D8 的 NAND 里固件损坏，开不了机。这台机器的资料在网上几乎绝迹，能找到的线索主要来自司徒大哥（steward-fu）分享的固件包与教程。在他的包基础上，我重新做出了可用的刷机包，一步一步把 4GB NAND 写回去。

- 🌐 网页详情：[zhengba-lab.pages.dev/#p/iriver-d8](https://zhengba-lab.pages.dev/#p/iriver-d8)
- 📦 刷机包：见 [`firmware/`](../firmware/)（或 Releases）
- 🔗 资料来源：[司徒大哥的教学站](https://steward-fu.github.io/website/index.htm)

## 机器关键参数

| 项目 | 值 |
|---|---|
| 存储 | 4 GB NAND |
| 根文件系统 | 248 MB ROOTFS 分区 · YAFFS2 |
| 内核 | Linux 2.6.24.3（2010-03-31 构建） |
| 刷写方式 | USB + PyUSB，页级读写 |

## 过程记录

### 第一步 · 先鉴定身份，别刷错机

古董机最容易踩的坑就是型号认错——同一个型号号可能跨品类（LG-P525 就是 2011 年的双卡功能机，不是 Optimus One 安卓机）。先把铭牌、摄像头像素标注、实体键字形这些硬证据对齐，确认手里的确实是 iRiver D8。身份没搞清之前，一个字节都不要往里写。

> 📷 待补图：机器铭牌 / 正面照 → `images/01-identify.jpg`

### 第二步 · 摸清 NAND 布局

把 4GB NAND 的分区结构读出来：其中 248MB 是 ROOTFS 分区，放的是 YAFFS2 根文件系统；内核是 Linux 2.6.24.3，编译日期 2010-03-31。布局清楚了，才知道该往哪个地址写什么。这一步是后面所有操作的地图。

> 📷 待补图：NAND 布局 / 分区表截图 → `images/02-layout.jpg`

### 第三步 · 发现块读取有 512KB 上限

实测发现一个要命的限制：一次性块读取超过 512KB 就失败。改用单页读取后稳定可靠。于是整个刷写策略从"整块读写"改成"逐页读写"——慢是慢一点，但每一步都可验证。

> 📷 待补图：单页读取实测 / 报错记录 → `images/03-page-read.jpg`

### 第四步 · 用司徒大哥的包，自制刷机包 ⭐

**整件事的关键转折。** 网上现成的包对不上，我在司徒大哥分享的固件包基础上，按这台机器实际的 NAND 布局重新组织、调整，自己做出了一个能用的刷机包。感谢司徒大哥把资料和包分享出来——没有这些底子，从零逆向一个 2010 年的固件几乎不可能。

> 📷 待补图：自制刷机包 / 文件清单 → `images/04-firmware.jpg`

### 第五步 · 逐页写入 + 页级校验

用 PyUSB 通过 USB 把刷机包按页写进 NAND。每写一页就读回来比对，页级校验确认无误再进下一页。整个写入过程不追求快，只追求每一页都对得上。

> 📷 待补图：写入过程 / 校验输出 → `images/05-flash.jpg`

### 第六步 · 启动链排查：`/linuxrc` 与 `init`

写完之后机器还是 panic。顺着启动日志追下去，发现卡在 `/linuxrc` 失败、init 缺失——根文件系统虽然写进去了，但启动链上少了关键的一环。这段还在继续排查，也是目前剩下的最后一道坎。

> 📷 待补图：启动 panic 日志截图 → `images/06-panic.jpg`

## 踩过的坑

1. **块读取超过 512KB 会失败** → 全程改单页读取，宁慢勿错。
2. **型号号容易跨品类认错** → 先靠铭牌 / 按键 / 屏幕比例鉴定身份，再动手。
3. **写完不等于能启动** → 还要单独查 `/linuxrc` 和 `init` 这两个启动链环节。
